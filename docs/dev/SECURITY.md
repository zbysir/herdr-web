# 安全设计

> **实现状态（2026-08-21）**：P0 三项 + L3 限速封锁 + **L2(c) passkey** 已实现（见 §12）。
> 还没做：令牌轮换与重用检测（L4）、审计日志、panic。
> 部署形态已定：**frp + 自己的域名 + 真证书**，不用 Tailscale，见 §8。

这个口后面是**一个登录 shell**，以及一个**能替你执行命令的 agent**（发件箱那条路即使
不开 PTY 也一样能让 agent 跑命令）。现在挡在前面的只有一层：一个永不过期、明文
http、跟在 URL 里的 token。不够。

下面是分层设计，每层可以单独上。文档只写**为什么这么选**和**怎么会静默出错**；具体
函数签名到实现的时候再定。

---

## 0. 先把优先级排对

要求里的三件事（2FA、轮换、错太多封 IP）都值得做，但**它们不是当前最大的洞**。先算
一下账：

- 现在的 token 是 96 位随机（`config.go` 里 12 字节 hex）。哪怕让攻击者跑到
  10k req/s（Go 在笔记本上都到不了），穷举期望时间是 `2^95 / 10^4` ≈ 4×10^24 秒，也就是 10^17 年量级。
  **这个 token 猜不出来。** 所以「猜错太多封 IP」防的不是它。
- 真正让人丢机器的是另外三条：**明文传输**（同一个 Wi-Fi 上抓包就拿到 token 和整个
  终端画面）、**凭据泄露**（token 在 URL 里 → 浏览器历史、书签云同步、截屏、二维码被
  拍走；落盘明文 → 被跑在同一台机器上的 agent `cat` 走）、**无法撤销**（丢了手机只能
  `rm token`，所有设备一起废，而且换完新 token 又是永不过期的一把）。

所以限速/封锁的真实作用是**保护那些短的凭据**（配对码、批准数字、TOTP 的 6 位）和
**让攻击动静可见**，不是保护那个 96 位 token。这一点决定了下面每层的必要性排序：

| 优先级 | 层 | 挡住的是 |
|---|---|---|
| **P0** | L0 传输加密 | 同网抓包、中间人。**没有这层，上面所有认证都是在明文里传** |
| **P0** | L1 凭据分层（配对码 + 可撤销的设备会话） | 凭据泄露、无法撤销、URL 里带秘密 |
| **P0** | L5 里的 Host/Origin 白名单 | DNS rebinding（一旦改成 cookie 认证就是真洞） |
| **P1** | L2 第二因子 | 配对码被抄走、落盘凭据被 agent 读走 |
| **P1** | L3 限速 + 封锁 + 告警 | 猜短凭据；让攻击可见 |
| **P1** | L4 轮换 + 重用检测 | 会话令牌被偷之后的长期潜伏 |
| **P2** | L5 其余（审计、panic、受限命令、响应头） | 事后追溯、缩小爆炸半径 |

## 1. 威胁模型

| 谁 | 现在能干什么 | 哪层挡 |
|---|---|---|
| **A1 局域网扫端口的** | 摸到 `:7788`，拿不到 token。但可以无限次试、无声无息 | L3 |
| **A2 同网抓包 / ARP 欺骗 / 恶意路由器** | **拿到 token + 看到整个终端画面**。当场结束 | L0 |
| **A3 凭据泄露**（历史记录、书签云同步、截屏、二维码被拍、herdr pane 里被别的 agent 读到启动横幅） | 拿到永久 shell | L1 L2 L4 |
| **A4 手机丢了 / 借人用过** | 永久 shell，除了换 token 没法单独踢掉 | L1 L4 |
| **A5 浏览器里的别的网站 / DNS rebinding** | 现在靠「秘密在 URL 里」侥幸免疫（外站不知道 token）。**改成 cookie 之后立刻变成真洞** | L5 |
| **A6 跑在这台机器上的 agent 被 prompt injection** | `cat ~/.herdr-web/token` 就拿到，或者把它打进某个 pane / 发到网上 | L1（只存哈希）L2（passkey） |
| **A7 外网**（端口转发 / 隧道没设认证） | A1–A4 全部放大到整个互联网 | L0 L2 L3 |
| A8 恶意浏览器扩展 / 被入侵的手机 | 全都完蛋，管不了 | — |

A6 值得单独说：**这个项目的存在意义就是驱动 agent**，而 agent 天天读不可信内容（网页、
仓库、issue 文本）。「一个明文长期秘密躺在 agent 读得到的路径上」在别的项目里是理论
风险，在这里是日常。这直接决定了 L1 的一条硬要求：**服务端不再落盘任何可以直接用来
登录的明文。**

## 2. L0 传输：先有 TLS，2FA 才有意义

在明文 http 上加 2FA 是自欺欺人 —— 抓包的人拿到的是**已经通过 2FA 的会话**，第二因子
一次也不用过。所以这层必须在最前面。

**不用 Tailscale**（已排除），所以证书得自己搞。按「每台设备第一次要点几下」排序：

1. **有自己的域名 → DNS-01 拿一张真证书**（最易用，零警告）。把 `herdr.你的域名` 的 A
   记录直接指到局域网 IP（`192.168.1.5`），用 DNS-01 challenge 签证书 —— 这个验证方式
   **不需要公网可达**，只要能改一条 TXT 记录，所以局域网 IP 也能拿到浏览器**默认信任**
   的证书。手机上零警告、零描述文件、是 secure context，连 passkey 的域名门槛都一起解决了。
   证书用 `lego`/`certbot` 之类的现成工具续，herdr-web 只需要支持
   `HERDR_WEB_TLS_CERT` / `HERDR_WEB_TLS_KEY` 指两个文件（十行）。
   代价：证书透明日志会公开这个域名（想避开就签通配符），以及 90 天要自动续。
2. **没有域名 → 自签 + 一次性 CA 描述文件**（每台设备装一次，之后零警告）。首启在
   `~/.herdr-web/tls/` 生成，SAN 里带上所有本机 LAN IP，IP 变了就重签；同时产一个
   `.mobileconfig`，扫码下载装一次，iOS 上就完全信任了（**要在真机上验一遍**）。
   以后想升级到 mTLS，就是往同一个 profile 里再塞一个 payload（见 §4.5）。
3. **懒得装 → 自签 + 每台设备点一次「继续访问」**。iOS 上是「显示详情 → 访问此网站」。
   能用，但这个例外**有时会自己失效**（清数据、系统升级），失效时表现是又一次警告页。
4. **已经有 nginx / Caddy** → 让它做 TLS，herdr-web 只听 127.0.0.1。Caddy 配一个内部 CA
   也能自动签，等价于第 2 条。

不管走哪条，都顺带修好一个老问题：http 不是 secure context，所以手机上 `OSC 52` 和
`navigator.clipboard` 是坏的；https（哪怕是手动接受的自签）`isSecureContext` 为真，
剪贴板就恢复了。

**默认策略**（这条比机制本身重要）：`Host` 不是 loopback 且没有 TLS 时**拒绝启动**，
错误信息里给出上面几条路和一个逃生口（`HERDR_WEB_INSECURE=1`）。现在的做法是打一行
警告然后照样起 —— 警告没人看。

### 域名和 443 都不是必须的

- **TLS 不需要域名。** 证书的 SAN 可以直接放 IP（`iPAddress` SAN），浏览器认，
  `https://192.168.1.5:7788` 是合法的 https 源，`isSecureContext` 为真。上面第 2 条就是
  这么签的。
- **端口和 TLS 无关**，443 唯一的好处是 URL 里不用写端口号。7788 上跑 https 没有任何
  问题（少数端口会被浏览器屏蔽，7788 不在名单里）。
- 域名只在**两件事**上是必须的，都不是 TLS 本身要求的：
  1. **想要浏览器默认信任的证书**。公共 CA 要做域名验证 —— 局域网 IP（`192.168.*`）
     没法做公开验证。**但有个绕法**：用一个自己的域名走 DNS-01，把 A 记录指到局域网 IP
     —— 见上面第 1 条，这是唯一能在局域网上拿到「浏览器默认信任」证书的办法。
     （Let's Encrypt 现在能给**公网** IP 直接签短期证书，局域网用不上。）
  2. **passkey / WebAuthn 的 RP ID**，见 L2(c)。这才是「弄个域名」的真正理由。
- 自己造的名字（hosts 文件、mDNS 的 `herdr.local`）能让 URL 好看点，但**证书还是得自签**，
  而且 `.local` 不在公共后缀列表里，**当不了 WebAuthn 的 RP ID** —— 所以它解决不了上面
  第 2 条。真要域名，就用一个**你自己拥有的真域名** + DNS-01（上面第 1 条）。

⚠️ **别发 HSTS。** 自签证书配上 HSTS，浏览器会把「点击继续」这个口也堵掉，直接变成
连不上、而且清不掉。只有第 1 / 4 条那种真证书下才考虑。

## 3. L1 凭据分层：配对码 + 设备会话

现在那一把 token 同时在干四件互相矛盾的事：引导凭据、长期会话凭据、所有设备共用、
放在 URL 里。拆成两件东西。

**目标定死**：**一台设备配一次，之后再也不用管。** 下面所有取舍都以这个为准。

### 为什么信任绑设备，不能绑 IP

「同一个 IP 免配对」听起来省事，但它两头都输：

- **IP 会被复用。** 客人来家里连 Wi-Fi，路由器从 DHCP 池里把 `192.168.1.23` 分给他 ——
  那正是你上周批准过的手机的地址。他打开页面就直接进你的 shell。这不是理论，DHCP 就是
  这么复用地址的。
- **IP 会变。** 手机重连 Wi-Fi、租约到期、路由器重启就可能换一个（iOS 的「专用 Wi-Fi
  地址」会让这更频繁）。于是**你自己反而要反复配对** —— 正好违反「一台设备配一次」。
- **IP 在局域网里可以直接冒用**：ARP 欺骗，或者趁你手机不在网上时直接占用那个地址。
  同一个二层网络里握手能正常完成，所以 IP 在这里根本不是身份。

所以身份必须落在**设备手里的一份东西**上：一个 cookie 里的随机令牌（本方案），或者一张
客户端证书（§4.5）。IP 只留两个作用：`--allow-cidr` 粗过滤，以及「换网段了」时在终端
提示一行（**只提示，不阻断**，否则又变成反复配对）。

### 配对码（bootstrap，一次性）

- 8 字符 base32（40 位），**只存在内存里**，进程重启就换一把。
- 有效期 5 分钟、**用一次就废**。启动横幅 + 二维码里编的是它。
- **扫码就是零输入**：扫 → 服务端验码 → 直接发 cookie → 302 到 `/`。一步，不用再输任何
  东西。当场生成的一次性二维码本身已经证明「你人在机器前」，所以默认不再叠第二道确认
  （想叠见 L2(a)，默认关）。
- **本机免配对**：来自 loopback 的请求直接信任 —— 能从 `127.0.0.1` 连上来的进程本来就
  已经在你机器上了，拦它没有意义。所以在机器上打开页面永远是零步骤。
- 用完之后想再配一台：在主机上敲 `herdr-web pair`（走 ctl.sock，见 L4），打印新码 +
  新二维码。
- **只有坐在机器前的人能出码。** 网页上没有任何出码的路径（理由见 §11）。局域网直连那条路
  用的是另一种东西 —— 短命、只能在直连口兑换、随上级一起被撤销的**交接令牌**，见 §11 的修正案。「登出之后
  码从哪儿来」的答案就是回到机器前敲一次 `herdr-web pair` —— 这个不方便正是那条安全
  性质本身。
- 于是**磁盘上再没有长期明文秘密**（A6 直接消失），二维码被拍走也只有 5 分钟窗口，
  URL 里的东西用一次就废，历史记录/书签同步泄露不再要紧。

### 设备会话（长期，per-device，可撤销）

配对成功后签发 256 位随机令牌，放 **cookie**：`HttpOnly; SameSite=Strict; Path=/`，
有 TLS 时加 `Secure`。服务端 `~/.herdr-web/devices.json`（0600）里**只存
SHA-256 哈希**外加元数据：设备 id、标签（从 UA 猜，可改名）、创建时间、最后活跃、
最后 IP、过期时间。

- **默认 90 天滑动过期**（每次用都续期），`HERDR_WEB_DEVICE_TTL_DAYS=0` = **永不过期**。
  天天用的设备永远不会被踢下线；想要「配一次管一辈子」就设 0，撤销改成纯手动。
- **不绑 IP、不绑 UA**。绑了就等于「换网/升级系统之后重新配对」，直接违反目标。
  被偷之后靠 L4 的重用检测收敛。
- 每台设备一条，能单独踢。
- **书签里不再有秘密**，`https://host:7788/` 就行 —— 而且 cookie 换了书签照样有效，
  「重启不变」这个 UX 目标反而更稳（现在是靠不换 token 换来的）。
- WebSocket 同源握手会自动带 cookie，`/pty` 不用再在 query 里挂秘密（顺带修掉「秘密
  出现在反代 access log 里」）。
- **一台设备可能有两份凭据**，因为 cookie 是 host-only 的：开了局域网直连
  （`HERDR_WEB_LAN_PORT`，见 [DEPLOY.md](DEPLOY.md)）之后，同一台平板在公网那个 origin
  和直连那个 origin 上各有一份，设备面板里出现两条。这是作用域决定的，不是重复登记 ——
  而且是个好性质：两份能分别撤销（「家里那份留着，公网那份踢掉」）。切过去那一下靠一个
  **一次性配对码**把凭据带过去（走的就是配对那条路，只是码由已认证的会话自己要），
  所以那一侧看起来「走了配对逻辑」是对的。

### 迁移路径（旧书签不能一夜作废）

`?token=<旧 token>` 保留，但**降级成只能引导**：命中就当一次配对，发 cookie，然后
302 到 `/` 把 URL 里的 token 抹掉。旧书签第一次打开自动升级成设备会话，之后那个 token
就可以随便换/删掉了。给一个 `HERDR_WEB_LEGACY_TOKEN=0` 关掉这条兼容路。

**迁移完就把 `~/.herdr-web/token` 删掉。** 只要那个文件还在，A6 就还在：被注入的 agent
读到它就能自己配一台设备进来。想留着又不想留这个洞，就设
`HERDR_WEB_LEGACY_TOKEN=loopback` —— **长期凭据只在 loopback 上有效**，局域网上进来
一律得走一次性二维码。这条规则很干净：泄露给「已经能在你机器上跑代码的东西」不算泄露，
它早就有你的 shell 了。代价是手机上的旧书签会失效一次，得重新扫一次码 —— 一台设备一次，
可以接受。

## 4. L2 第二因子

先把话说准，别自我催眠：

- **配对码是「主机屏幕上能读到的东西」，本机批准也是。**两个都走同一个渠道，严格讲
  不是两个因子，而是**现场证明（proof-of-presence）**。它抵消的是「配对码被抄走/被拍走」。
- **真正独立的第二因子**只有两种：authenticator 里的 TOTP 密钥，和设备里的 passkey 私钥。

三个都做，作用不同：

### (a) 本机批准 —— 现场证明，**默认关**

新设备配对时，服务端在**跑 herdr-web 的那个终端里**打一行：

```
  ⚠️  有设备要配对   iPhone · Safari · 192.168.1.23
      在浏览器上输入这 4 位： 8 2 4 1        （60 秒内有效，错 3 次作废）
```

**数字显示在主机、输入在浏览器**，不是反过来。理由：主机屏幕是局域网上的人读不到的
带外渠道，所以攻击者即使拿到配对码也过不去；而且不需要在主机上做交互式输入（服务
输出重定向到日志文件也照样能用），也不存在「弹确认框弹多了盲按 yes」这种疲劳攻击面。

4 位 = 10^4，**必须**配 L3 的限速（3 次错就作废，整体再受 IP 封锁约束）。

**默认关**（`HERDR_WEB_PAIR_APPROVE=1` 打开）。因为二维码本来就是当场生成、5 分钟过期、
用一次就废的，扫得到它基本等于人在机器前，再叠一道只是多输四个数字。要打开它的场合只有
一个：**配对码有可能已经泄露**（比如你把二维码截图发出去过、或者把 `pair` 的输出留在
某个 pane 里被别的 agent 读到）。另有一个更省事的变体：终端上直接问 `批准 iPhone /
192.168.1.23？[y/N]`，少输四个数字，代价是挡不住「攻击者已经有配对码」的情况 —— 因为
那时候你不知道弹出来的到底是谁。

### (b) TOTP —— 离机时的真第二因子

`herdr-web setup-2fa` 生成密钥，用现成的 `internal/qr` 把 `otpauth://` 二维码直接画在
终端里（这个包已经有了，白捡），扫进任何 authenticator。配对时要求「配对码 + 6 位」。

- stdlib 就够：`crypto/hmac` + `crypto/sha1` + `encoding/base32`，RFC 6238，约 60 行。
- 窗口 ±1 步（30 秒）。**必须记住上次用过的 step 并拒绝重放** —— 不然抓到一个 6 位数
  在 30~90 秒内可以重放，明文 http 下这就是现成的洞。
- 恢复口：你人就在机器前，`herdr-web reset-2fa` 就是恢复码，不用再搞一套一次性恢复码。
  只有「纯远程 + headless」那种形态才需要，那时候再加。
- **弱点要写清楚**：TOTP 密钥必须落盘，A6（被注入的 agent 读文件）能读走它。读走之后
  第二因子就没了，剩下的还是配对码 + 现场批准。所以 headless 场景别只指望 TOTP。

### (c) Passkey / WebAuthn —— 最强，但要域名

唯一一种**服务端存的东西泄露了也没用**的方案（服务端只有公钥），而且天然抗钓鱼、
手机上是 Face ID 一下。两个硬条件：

- 要 secure context（L0 给了）。
- **RP ID 必须是域名，裸 IP 不行**（`localhost` 是特例）。所以 `192.168.1.5:7788` 上
  做不了 passkey；Tailscale MagicDNS 的 `host.tailnet.ts.net` 或 CF Tunnel 的域名可以。
  **这一条和证书没关系**：把自签 CA 装到设备上、浏览器警告完全消失之后，裸 IP 上照样
  按不动 —— 门槛是「标识必须是域名」，不是「连接够不够可信」。

  实现上由此来的一条：**能不能用 passkey 要按请求的 Host 算**（`auth.UsableOn`），不能按
  「这个部署配了 RPID 没有」—— 开了局域网直连之后同一个部署同时有域名 origin 和裸 IP origin，
  按全局算会在 IP 那一侧交给前端一个 `available: true`，页面于是画出一个按下去只会抛
  SecurityError 的按钮。那几个 ceremony 的口也在裸 IP 上直接 409，而不是让 WebAuthn 库
  在后面报一个看不懂的 origin 错。

  由此来的一个实际后果（局域网直连那条路上）：`HERDR_WEB_REAUTH_HOURS` 的重验判据是
  **全局注册过几把 passkey**，不是「当前这个 origin 能不能用」。于是注册过 passkey 之后，
  裸 IP 那个 origin 过了重验窗口只能靠**重新配对**回来。要么把重验关掉，要么让直连地址
  也是个域名（内网 DNS 覆盖，或一条指向内网 IP 的公网 A 记录 —— DNS-01 不需要公网可达，
  那种记录一样能拿到真证书），然后把 `HERDR_WEB_RPID` 设成两个名字的上级域名，两个 origin
  共用一套 passkey。取舍写在 [DEPLOY.md](DEPLOY.md) 的「凭据在直连那一侧会怎样」。

结论：**已经在 Tailscale 上的话，passkey 是最优解**（可以直接替掉 TOTP）；裸 LAN IP
上就走 (a)+(b)。实现成本比 TOTP 高一个量级（注册 + 断言验证，或者引一个
`go-webauthn` 依赖），所以排在 P2，等真的要从外网连的时候再做。

### (d) 敏感操作的 step-up

第二因子只在**配对时**过一次（每次请求都要 6 位数的终端没法用）。但这几件事要求
「5 分钟内的新鲜认证」：配对新设备、撤销设备、改安全配置、panic。
可选：`HERDR_WEB_PTY_REAUTH_MIN`（默认关）—— 会话闲置超过 N 分钟后，**开新 PTY** 要
重新过一次因子。危险的是 shell，不是读接口。

## 4.5 备选路线：公私钥能替掉哪几层

「用 ssh 那套公私钥」是对的方向，但它不是一个机制，**在浏览器里有三种投影**，选错了
等于白干：

| 投影 | 是什么 | 结论 |
|---|---|---|
| **SSH 隧道** | herdr-web 只听 127.0.0.1，手机上用 SSH app 做 `-L` 端口转发，浏览器打 `http://localhost:7788` | 安全性最好懂，**但 iOS 一把 app 切后台就掐掉隧道**。iPad 分屏勉强，iPhone 基本不行。适合偶尔从外面连一次，不适合日常 |
| **mTLS 客户端证书** | TLS 层双向认证，每台设备一张证书，服务端只存指纹 | **最贴切的答案**，stdlib 三十行，一次替掉 L0 + L1。见下 |
| **passkey** | 应用层的公私钥，私钥在设备安全芯片里 | 最强，但要域名（L2(c)）。和 mTLS 不冲突，可以叠 |

**别做的第三种**：在网页里自己实现 ssh key 认证。浏览器摸不到 `~/.ssh/id_ed25519`
（没有文件访问），唯一的「实现方式」是把私钥粘进网页 —— 那是把长期私钥交给 JS 和
localStorage，比现在的 token 更糟。浏览器里能生成不可导出密钥（WebCrypto + IndexedDB），
但那已经不是「你的 ssh key」，而且各方面都不如 passkey。`<keygen>` 早被所有浏览器删了。

### mTLS 能替掉什么，替不掉什么

| 原来的问题 | mTLS |
|---|---|
| 明文传输 | ✅ TLS 本身 |
| 秘密在 URL / 明文落盘（A6 被注入的 agent 读文件） | ✅ 服务端只有**公钥指纹**，读走也没用 |
| 无法撤销 | ✅ `authorized_certs` 删一行，就是 `authorized_keys` 那个模型 |
| 猜凭据 / 要封 IP | ✅ 没有可猜的东西了，L3 降级成「只要告警和审计」 |
| 轮换 | ⚠️ 靠证书有效期（签 90 天，到期重新 enroll），不需要 L4 那套滚动轮换 |
| 第二因子 | ⚠️ 证书就是**单因子**：设备没锁屏被拿走就等于拿到。想要两因子还得叠 passkey，或者接受「设备锁屏就是第二因子」 |
| L5 那一整层 | ❌ **一点都替不掉**。尤其 DNS rebinding：攻击者的域名解析到你的 IP，浏览器该自动挑证书还是会挑，Host 白名单照样是 P0 |

### enroll 流程（保住扫码 UX）

```
herdr-web enroll ipad
  → 生成密钥对 + 自签客户端证书，指纹记进 ~/.herdr-web/authorized_certs
  → 生成 ipad.mobileconfig（同时装：信任我的 CA + 这台设备的身份）
  → 一次性 URL + 二维码（5 分钟）
手机扫码 → Safari 下载描述文件 → 设置里装一次 → 之后 https 没有警告、自动带证书
```

一个 `.mobileconfig` 里塞「根证书 + PKCS#12 身份」两个 payload，所以**装一次就同时**
解决了服务端证书不受信任和客户端证书两件事：之后是干净的 https（secure context，
剪贴板/`OSC 52` 恢复），没有任何警告。代价是每台设备多一次「装描述文件」，比扫码进来重。
**这条要在 iOS 真机上验一遍。**

实现上三个容易翻车的点：

- `ClientAuth` 用 **`RequestClientCert`**（要，但不强制）+ 自己在 `VerifyPeerCertificate`
  里比指纹。用 `RequireAndVerifyClientCert` 的话，没证书的设备会在 TLS 握手阶段就失败，
  浏览器只给一个 `ERR_BAD_SSL_CLIENT_AUTH_CERT`，**你没有任何机会告诉用户「去装描述文件」**。
- 客户端证书**从自己的 CA 签**（而不是纯自签），唯一目的是让 iOS/Safari 能在证书选择器里
  **自动挑对那一张** —— 服务端发的 acceptable-CA 列表是空的时候，有些客户端干脆一张都不给。
- 私钥是在**主机上**生成再送到设备的（浏览器没法自己造证书），所以那个一次性下载 URL
  是真正的敏感环节：一次性 + 5 分钟 + 只在 loopback/局域网、下载完立刻从内存里删。
  ssh 那边是在客户端生成密钥、只传公钥，这一点上 mTLS 天生弱一档。

### 所以怎么选

- **人在 iPad 上、不想依赖外部服务** → mTLS。替掉 P0 里的「自签 TLS + 配对码 + 设备会话」
  三项，剩下 L5 全部保留、L3 只留告警和审计。总工作量比原方案小。
- **能接受依赖一个服务** → Tailscale。它本身就是「每台设备一对公私钥 + 可撤销 + iOS 后台
  常驻」的成品，`tailscale cert` 顺带给真证书和域名，域名一到手 passkey 也能上。工作量最小、
  上限最高。
- **两个都不想** → 回到原方案（配对码 + 设备会话 cookie + 本机批准）。

## 5. L3 限速、封锁、告警

计数只在**认证失败**上做，已经有合法会话的设备完全不走这道闸（不然攻击者可以拿你的
IP 陪葬）。

- **每 IP 指数退避**：前 2 次免费，之后响应前先 sleep `min(2^(n-2), 30)` 秒。
- **封锁**：15 分钟内失败 ≥10 次 → 封该 IP 15 分钟；重犯翻倍，上限 24 小时。回 429 +
  `Retry-After`。
- **loopback 永不封**，否则一台机器上就能把自己锁在门外。
- **全局熔断**：所有 IP 的失败总数超阈值（换源 IP 的分布式尝试）→ 进入 lockdown：
  **拒绝一切新配对**，直到主机上敲 `herdr-web unlock`。已有会话不受影响 —— 宁可不让
  新设备进来，也别把正在干活的自己踢下线。
- **动静要看得见**：现在被人猛猜 token 是完全无声的。封锁触发时在终端打一行醒目的
  `有人在猜配对码：192.168.1.77 已封 15 分钟（第 3 次）`，并写审计日志。
- 所有短凭据比较都走 `crypto/subtle`，并且**错误响应形状一律相同** —— 别让「没有这个
  设备」和「码不对」能被区分出来。
- 状态放内存（`map[string]*entry` + mutex + 惰性清理）。重启即清，但重启需要主机权限，
  能重启的人早就赢了。不落盘换来的是不用管文件损坏和并发写。

## 6. L4 轮换

三种东西，三种轮换方式：

| 东西 | 怎么换 |
|---|---|
| 配对码 | 一次性 + 5 分钟过期，进程重启换新（等于强制轮换） |
| 设备会话令牌 | 滚动轮换 + **重用检测**，见下 |
| 旧的 `token` 文件 | 降级成引导用，随便换随便删，**不再影响已配对的设备** |

**滚动轮换 + 重用检测**（这条是「token 轮换」真正值钱的地方）：

- 每台设备的会话令牌用满 24 小时就在下一次请求时换新的，`Set-Cookie` 顶掉旧值。
- 旧值留 60 秒宽限（并发请求和 WebSocket 重连会同时在飞，不给宽限会随机掉线）。
- **宽限期过后又有人拿旧值来** → 这只有两种解释：偷了 cookie 的人在用，或者你自己的
  设备状态回滚了。两种都按最坏处理：**吊销这台设备的整条会话链**，逼它重新配对，
  终端上打一行告警 + 审计日志记下 IP/UA。
- 这是 cookie 被偷之后唯一能自动收敛的机制，因为 cookie 没法绑 IP（手机在 Wi-Fi 和
  蜂窝之间跳，绑了就天天掉线）。

**撤销的操作面**（都要能在没有浏览器的情况下用）：

```
herdr-web devices              # 列出已配对设备：标签 / 最后活跃 / 最后 IP
herdr-web revoke <id> | --all  # 踢掉
herdr-web pair                 # 打印新配对码 + 二维码
herdr-web setup-2fa | reset-2fa
herdr-web unlock               # 解全局熔断
herdr-web panic                # 全撤销 + 杀掉所有 PTY + 停掉非 loopback 监听
```

走 `~/.herdr-web/ctl.sock`（0600），**认证靠文件权限**，和这个项目已经在用的 herdr
socket 是同一个套路。服务没在跑时这些子命令直接改文件。

网页上也给一个「断开所有设备」，用软键条已有的**「两下才生效」**那套防误触 UX。

## 7. L5 缩小爆炸半径

认证总有一天会失效，所以这些和认证一样重要：

1. **Host / Origin 白名单**（P0，一旦上 cookie 就必须有）。只接受 `Host` ∈ {loopback、
   实际绑定的 IP、配置的域名} + 端口，其余回 421。这挡的是 DNS rebinding：攻击者的
   页面把自己的域名解析到 `127.0.0.1`，浏览器眼里就是同源，cookie 会照发。同时把
   `pty.go:59` 的 `CheckOrigin` 收紧 —— 现在 `Origin` 为空就直接放行（给非浏览器客户端
   留的口），改成「带 cookie 的请求必须有匹配的 Origin」。
2. **CSRF**：`SameSite=Strict` + 上面的 Origin 校验 + 所有写接口要求一个自定义头
   （跨站发不出来，会被 preflight 挡住）。注意 `/api/herdr/upload` 收的是裸字节、
   content-type 是 `image/png`，属于 CORS simple request，是这些接口里唯一能被跨站
   直接 POST 的 —— cookie 上了 SameSite 之后才算真堵住。
3. **`--allow-cidr`**：只接受来自 `192.168.1.0/24` 的连接。不能当主要防线（局域网 IP
   随便伪造、DHCP 还会变），但能把「路由器上的访客网络」这类顺手挡掉。
4. **PTY 并发上限**（默认 4）。现在一条 WebSocket 就起一个登录 shell，没有上限；
   README 里那个「连接按钮随时能按」的坑本质上就是这个。
5. **审计日志** `~/.herdr-web/audit.log`（0600，JSON lines，5 MB 轮转）：配对、撤销、
   失败、封锁、PTY 开关（带设备 id）、投稿（目标 + 字数，**不记内容**）、上传。
   凭据一律只记 `sha256(值)` 的前 8 位 hex —— 能对上是哪一把，又不落明文。
6. **安全响应头**（`static.go` 现在一个都没有）：
   `Content-Security-Policy: default-src 'self'; connect-src 'self'; img-src 'self' data: blob:; style-src 'self' 'unsafe-inline'; frame-ancestors 'none'; base-uri 'none'; form-action 'none'`、
   `Referrer-Policy: no-referrer`、`X-Content-Type-Options: nosniff`、`X-Frame-Options: DENY`。
   `connect-src 'self'` 顺带保证被注入的前端代码没法把终端内容外发。
7. **OSC 8 链接加 scheme 白名单**（`session.ts:95`/`:99`）：终端里显示的东西是
   **agent 完全可控**的，而 `window.open` 现在什么 URI 都开。只放 `http/https/mailto`，
   其余提示不打开。现代浏览器基本会拦 `javascript:`/`data:` 的顶层导航，所以这条严重
   性低，但改动是三行。
8. **受限命令**：`HERDR_WEB_CMD="herdr attach"` 替掉登录 shell。要说实话 —— 这**不是
   边界**（herdr 里照样能开 shell），它只是把「拿到会话立刻一行 `rm -rf`」变成多几步。
   真隔离要单独 unix 用户或容器，那和「我要的就是我自己的开发环境」直接冲突，不做。
9. **发件箱和 `/pty` 同一个权限档**。容易想错的地方：以为 `/api/herdr/say` 比 `/pty`
   轻。它是往一个能执行命令的 agent 嘴里塞话，等价于代码执行。别给它更松的认证。
10. **cookie 不区分端口**。同一台主机上另一个端口的 web 服务会收到我们的会话 cookie
    （HttpOnly 只挡 JS 读，挡不住浏览器发）。`__Host-` 前缀也治不了这个，没有解法，
    只能写在文档里：**别在同一台机器上跑不可信的 web 服务**。
11. **文件浏览（`/api/files/*` + `/_f/`）和 `/pty` 同一个权限档，但多了一个新面**：
    它会把**agent 写的文件**从本站的源上吐出去。这里最危险的不是「能读哪些路径」——
    能开这个页面的人已经有一个 shell，读什么都拦不住，所以默认**不设** jail
    （`HERDR_WEB_FILE_ROOTS` 才是）。危险的是**吐出去的东西被浏览器当成什么**：
    同源的 `text/html` 就是一个能调 `/api/herdr/say` 的跳板（HttpOnly 只挡 JS 读 cookie，
    而它根本不用读 —— 浏览器会自动带上）。所以只有**认出来的图**（png/jpg/gif/webp 按魔数，SVG 按开头）
    才 inline，其余一律 `application/octet-stream` + `attachment`，响应上再压一条
    CSP `sandbox`。文本预览走 JSON 由前端画进 `<pre>`，那条路上根本没有「浏览器解释
    这段内容」的环节。
    **SVG 是唯一一个「能跑脚本却照样 inline」的类型**，因为它有两条各自独立的保障：
    查看器里走 `<img>`（规范的 secure static mode，脚本不跑、外链不加载，**不依赖任何
    响应头**），顶层打开靠 `sandbox`（不给执行 + opaque 源）外加 `default-src 'none'`。
    改这块之前先读 `internal/files` 的包注释 —— 把 `<img>` 换成内联 `<svg>` 或
    `innerHTML`，就是一个直接的同源 XSS。
    另外 `/_f/<票>` 是**唯一一条不看 cookie 的口**（`<img src>` 设不了 CSRF 头）：
    票绑死一个绝对路径、15 分钟过期、密钥进程内随机生成不落盘。它在 URL 里，
    所以会进浏览器历史和截图 —— 拿到的人在 15 分钟内能读**那一个**文件。

## 8. 部署形态：frp + 自己的域名（已定）

不用 Tailscale。实际形态是 **frpc 在本机、frps 在公网 VPS**，域名是自己的。

```bash
HERDR_WEB_EXPOSED=1 \
HERDR_WEB_TLS_CERT=…/fullchain.pem HERDR_WEB_TLS_KEY=…/privkey.pem \
HERDR_WEB_HOSTNAME=herdr.example.com \
HERDR_WEB_PUBLIC_URL=https://herdr.example.com:17788 \
./herdr-web
```

三个关键决定：

1. **frp 用 `type = tcp`，TLS 由 herdr-web 自己终止。** 这样 frps 那台 VPS 上只有密文。
   用 frp 的 https 模式（`vhost_https_port`）就是在 VPS 上解密，那台机器能看到你的整个
   终端画面 —— 除非完全信任它，别这么配。
2. **证书用 DNS-01 签。** 不需要公网可达，只要能改一条 TXT 记录，所以 A 记录指到哪儿都
   行。拿到的是浏览器默认信任的证书：零警告、零描述文件、是 secure context，而且**域名
   一到手 passkey 的门槛也没了**（见 L2(c)）—— 这是这个形态最大的红利。
3. **公网暴露把 L3 从 P1 提到 P0。** 局域网上「有人在猜」是偶发，公网上是持续背景噪声。

### frp 把两个默认策略打穿了

这是这次设计里最容易送掉 shell 的地方，单独记：

- **「监听地址不是 loopback 才要求 TLS」失效。** 走 frp 时 herdr-web 往往只监听
  `127.0.0.1`（frpc 从本机连），看起来是最安全的配置，实际暴露在整个互联网上。没有任何
  办法自动测出来 → 必须手动 `HERDR_WEB_EXPOSED=1` 声明，声明之后才强制 TLS。
- **「本机免配对」变成「公网免配对」。** 穿透进来的请求源地址就是 `127.0.0.1`。所以这个
  豁免**改成默认关**，打开时还额外要求 `Host` 也是 loopback 字面量（浏览器地址栏里是
  域名时 Host 就是域名，穿透进来的请求过不了这一条）。
- **拿不到客户端真实 IP，而这会把整层限速变成空操作。** tcp 模式下所有人在 herdr-web
  眼里都是 `127.0.0.1` —— 撞上「本机永不封」（那条本来是防止把自己锁在门外）之后，
  限速一次都不会生效。**看起来配了、实际没有**，这是这次实现里最阴的一个坑。
  所以 `Exposed`（或 `TrustProxy`）时自动关掉 loopback 豁免；代价是有人猛试的时候你自己
  也配不了新设备，用 `herdr-web unlock` 解。要真实 IP 就在 frpc 上开
  `transport.proxyProtocolVersion = "v2"`（herdr-web 还得会解 PROXY 头，现在不会），
  或者用 http 模式让 frps 加 XFF（那时候才配 `HERDR_WEB_TRUST_PROXY=1`）。
- **`X-Forwarded-For` 默认不信。** 没有可信前置时读它，等于让攻击者自带一个头就换个源 IP，
  把限速和封锁绕干净。

### 之后还会在 VPS 上再部署一个

同一个域名下两套 herdr-web（一套穿透回 Mac，一套直接跑在 VPS 上）。差别在这几处：

- **那边能拿到真实客户端 IP**，所以按 IP 的限速才是真的按 IP，「本机永不封」也可以留着。
  判据不是「暴露了没有」而是「拿到的 IP 是不是客户端的」：`TrustProxy || !Exposed`。
- **证书那边好办**：80 / 443 空着就直接 HTTP-01 / TLS-ALPN-01，不用折腾 DNS-01。
- **两套凭据完全独立**（各自的 `devices.json`），要各配一次对。
- **passkey 可以共用**：两个部署用不同子域时，把 RP ID 设成父域 `bysir.top`，一个 passkey
  两边都能用。代价是这个凭据对 `*.bysir.top` 下所有站点有效 —— 那些子域全是你自己的才行。
- **VPS 上那个 shell 往往是 root**，比 Mac 上那个更值钱。用非 root 用户跑，或者
  `HERDR_WEB_SHELL` / 将来的 `HERDR_WEB_CMD` 收窄。

### 另外两种形态（留着对照）

| 形态 | 配什么 |
|---|---|
| **只本机**（`127.0.0.1`，默认） | `HERDR_WEB_TLS=off` + 可选 `HERDR_WEB_TRUST_LOOPBACK=1`（零配对）。loopback 上 http 已经是 secure context |
| **局域网** | `HERDR_WEB_TLS=auto` 自签（本地 CA + 397 天叶子）+ 每台设备第一次点一下「继续访问」，或者装一次 CA |

## 11. 不做什么，为什么

- **IP 白名单当主要认证** —— 局域网 IP 随便伪造，DHCP 还会变。只当附加过滤（L5.3）。
- **用户名密码** —— 比现在的 96 位随机 token 更弱（人会挑烂密码），还得管哈希和改密流程。
- **换个隐蔽端口 / 不打横幅** —— 不是安全机制。
- **每次请求都过第二因子** —— 终端会没法用，而且会训练出「无脑点确认」的习惯，反而更糟。
- **自己写除 TOTP（就是 HMAC）以外的任何密码学** —— 签名/加密一律用 stdlib 或成熟库。
- **cookie 绑 IP** —— 手机在 Wi-Fi/蜂窝之间跳，会天天掉线。改用 L4 的重用检测收敛。
- **在网页上出配对码** —— 不管请求方认证没认证。理由不是「会不会提权」（已配对的设备
  本来就有你的 shell），而是这两条：
  1. 配对码创造的是一份**独立的、长期的、不随创造者一起被撤销的**凭据。手机被人拿去
     一次，他配一台自己的设备进来；你之后把手机踢掉，**他那台还在**。这是绕过撤销的
     持久化，和「他能用你手机干什么」是两回事。
  2. 在这个项目里更要命：码是打在终端里的，而那个终端往往是个 herdr pane —— 同 session
     的 agent 能 `pane.read` 读到它。只要外面的人能远程触发「打一个码」，「触发打印 +
     被注入的 agent 读走」就是一条完整的远程配对链，人根本不用碰机器。

  所以配对码只能由坐在机器前的人产生（`herdr-web pair` 或启动横幅）。在 L2 的第二因子
  做出来之前，「能读到那个终端」是整套里**唯一的带外因子**，不能为了省一趟路把它拆掉。

  **修正案（局域网直连）**：直连是另一个 origin，cookie 是 host-only 的，所以那一侧总得有
  一份自己的凭据。第一版实现图省事直接调了 `MintCode()` —— 那就是上面这条禁令本身，一份
  被偷的 cookie 成了无限发凭据的机器。现在换成一种**单独的交接令牌**（`auth.MintHandoff`），
  它在三处比配对码窄，正好把上面两条理由各堵一遍：

  1. **随上级一起被撤销**：兑出来的设备记着 `Parent`，`Revoke(上级)` 会把它一起摘掉 ——
     第 1 条那个「踢掉手机他那台还在」不成立了。
  2. **只能在直连那个监听上兑换**，且那个口**只服务本地网络**（见下面那条）—— 于是最坏
     情况也只是「一份只能从你家里用、且随上级一起死的凭据」，不是一份通用凭据。
  3. **不打进终端**，所以第 2 条那条链（打印 → 同 session 的 agent `pane.read` 读走）
     压根不存在。另外它 60 秒过期、一次性、256 位随机（猜不动，所以不进限速那一层）。

  这里有一处**判据不能看错**：「是不是从直连口进来的」只能按**请求落在哪个监听上**算，
  不能看 `Host` —— `hostOK` 对 IP 字面量一律放行（那是对的），所以公网那条路发一个
  `Host: 192.168.1.5:7790` 就能把「看起来像内网」伪造出来。

  而「绑通配地址 = 只有局域网碰得到」**本身也只是个拓扑假设**，至少三种情况下不成立：
  路由器上做了端口转发 / 开了 UPnP；隧道配错转到了这个口；以及最隐蔽的那种 ——
  `net.Listen("tcp", "0.0.0.0:port")` 在 Go 里开的是**双栈**套接字，而家宽 IPv6 通常没有
  NAT，一台有全局 IPv6 的机器上这个口是否公网可达只取决于路由器防火墙。所以直连那个口
  加了一道**对端地址必须是私网 / 链路本地 / 本机**的检查（`lan.PeerIsLocal`），非本地对端
  一个字节都不服务（403 + 日志里告警一次）。有了它，「从直连口进来」才是一条**被强制的**
  性质，而不是一句祈祷。

## 13. 实现时会静默出错的地方

按这个仓库的惯例，先把坑记下来：

- **HSTS + 自签证书 = 自己把门焊死**，浏览器不再给「继续访问」，而且清不掉。别发。
- **cookie 加了 `Secure` 之后再退回 http，登录会静默失效**（cookie 压根不发），表现是
  「一直跳回配对页」而不是报错。loopback 上不要加 `Secure`。
- **轮换不留宽限期就会随机掉线**：WebSocket 重连和轮询（500ms 一拍的自动拉回）会同时
  在飞，两个请求撞在轮换点上，其中一个必然拿着旧值。60 秒宽限是必需的，不是保险。
- **TOTP 不做重放拒绝等于没做**：一个 6 位数在窗口内可以重复用，明文 http 下抓一次就够。
- **`CheckOrigin` 里 `Origin == "" → true`** 是个现成的口：任何非浏览器客户端不带这个头
  就绕过去了。现在因为秘密在 URL 里所以不算洞，改 cookie 之后就是洞。
- **loopback 的封锁豁免是把双刃刀**：不豁免，第一次调限速就把自己锁在门外（解锁入口还在
  门后面）；豁免了，穿透部署下整层限速直接空转（所有请求都是 127.0.0.1）。所以它跟着
  `Exposed` / `TrustProxy` 走，不是一个常量。
- **审计日志别记投稿内容**：那是口述的原始文本，可能包含任何东西，落盘还是 0600 的
  明文。要记就单独开关，默认关。
- **走 frp 时「监听 127.0.0.1」不等于安全**，反而是最危险的组合：暴露检测和本机豁免
  两个判据同时失效。必须 `HERDR_WEB_EXPOSED=1`。
- **`HERDR_WEB_PUBLIC_URL` 不给，横幅上的二维码就是废的**：frp 的公网端口和本地监听端口
  经常不一样，进程自己猜不出来，扫了会连到一个不存在的地址上。
- **设备凭据别放 localStorage。** iOS 的 ITP 会把「脚本能写的存储」（localStorage、
  IndexedDB、`document.cookie` 写的 cookie）在**站点 7 天没交互后清掉** —— 表现就是
  「隔一周回来又要重新配对」，正好是这次最想避免的事。服务端 `Set-Cookie` 发的
  HttpOnly cookie 不受这个 7 天上限约束，所以凭据只能走它。
- **加到主屏幕（PWA）之后可能要再配一次对**：iOS 上主屏幕 web app 的存储容器和 Safari
  是分开的，Safari 里配好的 cookie 带不过去。**要在真机上验一遍**；真是这样就在文档里
  写明「先加到主屏幕，再在里面扫码配对」这个顺序。
- **配对码打在终端里，而那个终端可能是个 herdr pane** —— 同 session 的别的 agent 能用
  `pane.read` 把它读走（这个项目的发件箱就是这么读 pane 的）。窗口是 5 分钟 + 一次性，
  而且只在你主动出码时才存在。**曾经有过一版让配对页远程触发出码，那会把这条从「要知道
  有这条路」变成一条完整的远程配对链**（触发打印 + 被注入的 agent 读走），已经撤掉。
  再不放心就在 herdr 之外的终端里 `herdr-web pair`，或者开 L2(a) 的本机批准。
- **`devices.json` 只存哈希这条不能打折**。一旦为了省事存了明文，A6（被注入的 agent
  读文件）就整层复活，而这层是这次设计里最值钱的一条。

## 文件浏览这条路

（原来在 README「文件浏览」那节。吐出去的是 **agent 写的文件**，所以这条路的规矩和门那套是同一个量级的东西。）

#### 链接那条路：`/_f/<票>`

图片走的是一条**不带 cookie** 的短时链接。必须这样：`/api/*` 上 cookie 认证的请求要求
一个自定义头（CSRF 第三道防线），而 `<img src>`、「在新标签打开」、iOS「长按存到相册」
**都设不了头** —— 走 `/api` 一律 403。

票是能力凭据不是身份凭据：**绑死一个绝对路径**、15 分钟过期、签名密钥进程起来时随机
生成且**只在内存里**（重启即全废，磁盘上不多一个长期秘密）。代价说清楚：票在 URL 里，
所以会进浏览器历史、会出现在截图里，谁拿到那串东西在 15 分钟内就能读那**一个**文件。

#### 这条路上四条硬规矩

一条都不能少，因为吐出去的是**agent 写的文件**：

1. **绝不以 `text/html` 吐内容。** 同源的 HTML 就是一个能调 `/api/herdr/say` 的跳板
   （cookie 是 HttpOnly，但它根本不用读 cookie，浏览器会自动带上）—— agent 写个 html
   你点开就把 herdr 交出去了。只有认出来的图 inline，其余一律
   `application/octet-stream` + `attachment`。
2. **只读常规文件。** 点进 `/dev/zero` 就是一条无限流，`/dev/rdisk0` 更糟。设备 /
   socket / 管道在目录里照样列出来（列表要说实话），只是打不开。
3. **响应上再压一条 CSP `sandbox`**，覆盖全局那条。前两条哪天被改坏了还有这一层。
   **SVG 再多收一档**，见下。
4. **配了 `FILE_ROOTS` 时，前缀检查在 `EvalSymlinks` 之后做**，而且比 `root + 分隔符`
   —— 少任何一条都是静默放行（软链能指出去、`/home/user` 会放行 `/home/user2`）。

#### SVG 为什么敢渲染

SVG 是**能跑脚本**的图片（`<script>`、`onload=`、`<foreignObject>`），所以它安不安全
完全取决于**以什么身份被渲染**。两条路各自独立成立，任何一条单独都够：

| 路径 | 靠什么 |
|---|---|
| 查看器里的 `<img src=…>` | 规范规定的 **secure static mode**：`<img>` 里的 SVG 一律不跑脚本、不加载外部资源。**这条不看任何响应头**，前置代理把 CSP 剥了也还在 |
| 「在新标签打开」（顶层文档） | `/_f/` 上那条 CSP `sandbox` —— 没有 `allow-scripts` 就是不给执行，而且源是 opaque 的，跑起来也碰不到本站 API。再加 `default-src 'none'` 堵掉「svg 里塞个外链、你一打开就发一个请求」（style 放行，不然图表画出来一片黑） |

所以**别把 `<img>` 改成内联 `<svg>` 或 `innerHTML`** —— 内联进 DOM 的 SVG 是本页面的
一部分，agent 那段脚本就跑在我们的源上了。这一条写在 `FileViewer.tsx` 那个 `<img>` 上面。

认 SVG 的判据故意保守：BOM / 空白之后第一个字符必须是 `<`、采样里有 `<svg`、而且
**不能有 `<html`**。「一份 HTML 里顺手嵌了个 svg」必须走附件 —— 认错的代价不对称，
把 svg 认成文本只是看到源码，把 html 认成 svg 就是把一个能跑脚本的文档 inline 出去了。
